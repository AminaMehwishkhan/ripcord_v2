# Evaluation

> This file is generated by `benchmark/make_report.py` from `benchmark/results/benchmark_results.json`. Do not edit the numbers by hand.

## What was measured

**297 test calls** the system had never seen: the voices and the order numbers are different from the training and validation data (splits are made by speaker and by number). Each call is one caller saying a 4-digit order number, run through the real pipeline (`entity_detector` → risk engine → `SessionOrchestrator`). If a policy asks a question, the caller's recorded reply ("yes, that's right" or "no, it's …", also run through the recogniser) is played back, so the final result includes the recovery.

On this data the recogniser alone hears **47.1%** of the numbers wrong (and finds no number at all in 2.0% of calls). That is a harsh setting on purpose: it gives the safety layer something to do. A premium recogniser would make fewer errors, so read the *comparison between systems*, not the absolute rates.

In a live call the agent would ask again or hand over to a person, so these are safe, not wrong. They are high because the benchmark replays only one reply per call.

## What the numbers say

- **The plain agent acts on a wrong number 46% of the time** with this recogniser. Ripcord v2 brings that to **2.7%** (95% CI 1.0%–4.7%), and it resolves 57% of calls correctly (plain agent: 52%).
- **On wrong actions, v2 cannot be told apart from ASR confidence threshold, Weakest-digit threshold, Ripcord v1 (hand-tuned rules)** (confidence intervals overlap). Almost all of the gain comes from one simple fact: most of this recogniser's mistakes drop or garble digits, so the capture is not 4 digits long, and every system that checks the digit count and asks a question catches them. The learned scorer is not what makes the difference here.
- **v2 versus v1 (hand-tuned rules):** similar safety, but v2 asks needless questions on 8% of correctly heard calls against v1's 22%.
- **Always reading back never acts on a wrong number (0.0%), but it is the most annoying:** 1.64 questions per call, and only 34% of calls finish correctly in one round.

### The hard case: a wrong number that looks normal

A wrong length ("one five zero") is easy to spot. The dangerous mistakes are wrong numbers that still look like a normal 4-digit order number. **The test set has only 7 of them**, so nothing about this case can be concluded from the test set alone. At the chosen operating point:

| System | Valid-looking wrong numbers caught |
|---|---|
| ASR confidence threshold | 0% (0%–0%) |
| Weakest-digit threshold | 0% (0%–0%) |
| Ripcord v1 (hand-tuned rules) | 14% (0%–43%) |
| Ripcord v2 (learned) | 0% (0%–0%) |

A larger sample: on the **528 well-formed captures in train+validation (32 of them misheard)**, using cross-validated predictions for the learned model, the ranking quality (AUROC, 0.5 = coin flip) is:

| Score | AUROC, well-formed captures only |
|---|---|
| Ripcord v2 (learned) | 0.8002 |
| ASR confidence threshold | 0.4827 |
| Weakest-digit threshold | 0.4615 |

So for this recogniser, its own confidence scores say almost nothing about whether a well-formed number is right. How the number was *said* (as one big number, in pairs) and how fast says more. On the test set's 7 cases the same pattern shows (v2 0.7542, ASR confidence 0.3224), but with 7 positives that is only a hint.

This is also why the model is retrained per recogniser: a recogniser whose confidence is informative would weight it more.

## Where Ripcord fails

With Ripcord, **8 of 297 calls** (2.7%) still ended on a wrong number. Each is a wrong number that looked like a normal 4-digit order number. Heard / actually said / weakest-word confidence:

- snr25: heard **1456**, caller said **9456**, weakest word 0.54 — "looking reference named thousand four hundred fifty six"
- snr15: heard **9660**, caller said **9668**, weakest word 0.75 — "it's old and ninety six sixty e"
- snr10: heard **1196**, caller said **9196**, weakest word 0.63 — "looking reference men thousand one hundred ninety six"
- snr10: heard **9216**, caller said **9260**, weakest word 0.61 — "book in reference nine thousand two hundred sixteen"
- snr0: heard **2768**, caller said **1768**, weakest word 0.48 — "his order ones for them six eighth"
- clean: heard **1819**, caller said **1890**, weakest word 0.77 — "my confirmation court as eighteen nineteen"
- snr15: heard **1495**, caller said **4295**, weakest word 0.54 — "i'm calling about all the fourteen nine five"
- snr5: heard **7523**, caller said **7520**, weakest word 0.51 — "yes said the older number is seven thousand five hundred twenty three"

7 of the 8 listed were said as "… thousand … hundred …" or in pairs ("eighteen nineteen"), where the recogniser merges or swaps words and still produces four digits. Their weakest-word confidence ran from 0.48 to 0.77, so the recogniser's own score was not a reliable warning. The caller's own corrections and a read-back of every number are the other defences.

## How the model was trained

- A logistic regression over 12 explainable features of how the number was heard (confidence of the number words, spoken style, homophone digits, speaking rate and so on). Weight signs are constrained to common sense (more confidence never raises risk) so the explanations in the dashboard are trustworthy.
- It is fitted on **well-formed captures only** (the hard case). A wrong digit count is handled by a rate measured on the training data (99.8% of such captures were wrong), because those are almost always wrong and are easy to see.
- Trained on the train + validation splits only (1091 examples; 528 well-formed, 32 of them misheard). 5-fold cross-validation chose the regularisation: the strongest setting within one standard error of the best (λ = 0.03, shrunk toward a prior that lower confidence means more risk, which only matters because there are so few misheard examples). The question threshold (0.14) also comes from cross-validation. The test split was scored only after all of that was fixed.
- The threshold comes from a cost model: acting on a wrong number costs 10× as much as asking one question. Raise `--cost-ratio` in `train_risk_model.py` for higher-stakes workflows.
- The threshold baselines are tuned with the same cost model on the same well-formed captures, and they also get the digit-count check for free, so the comparison is not a straw man.

### What changed after the first test run

The first time the test split was scored it exposed a bug in the session logic: if the first capture had the wrong number of digits and the caller's reply was garbled, repeating the same malformed number could be "confirmed". It is fixed (a malformed number can never be verified, enforced in the orchestrator and again in the action layer, with regression tests) and the test split was scored again with the **same trained model**. No model weight, threshold or selection rule was changed after looking at test results.

## Data

- 900 generated calls (450 train / 153 val / 297 test), 109 speakers.
- Speech: VITS / VCTK (109 voices). Recogniser: sherpa-onnx streaming Zipformer (English, int8). Conditions: clean, five noise levels, phone-line band-limiting, echo, and fast speech.
- Each call includes the caller's recorded "yes" and "no, it's …" replies.

## Honest limits

- **The voices are synthetic** (text-to-speech), not real callers. Real people hesitate, interrupt and mumble in ways TTS does not.
- **The recogniser is an open-source model**, not AssemblyAI. Its confidence scores behave differently, so the trained weights and the threshold should be re-fit on your own recogniser's output before you trust absolute numbers. The pipeline, tests and training script are built so that is a one-command job (`benchmark/README.md`).
- **One entity type** (a 4-digit order number) in one simulated workflow.
- **Replies are recorded once per call.** If the restated number is misheard again, the system asks again; the benchmark only plays one reply, so those calls count as unresolved rather than being walked through every retry. This overstates the unresolved rate for every system.
- **Tests of the caller correcting a number already accepted** (the second chance for a confident-but-wrong capture) are in the unit tests and the dashboard, not in these numbers: each call here is a single utterance.
- The 10 hand-written scenarios in `demo/scenarios.json` are illustrations for the dashboard and are not part of these numbers.
